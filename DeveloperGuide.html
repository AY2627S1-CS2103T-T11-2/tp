TutorTrack Developer Guide

Acknowledgements

TutorTrack is based on AddressBook-Level3 by the SE-EDU initiative. It uses JavaFX, Jackson, and JUnit 5.

Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.
  • uses PersonCard to hide empty Phone and Telegram handle labels; a person with no tags has no tag labels.

Command history

CommandHistory stores up to 100 submitted commands independently of the JavaFX components. Consecutive exact duplicates are stored only once, while commands that differ in case remain distinct. This allows its navigation behaviour to be tested using regular unit tests.

CommandBox saves user-entered text as a separate draft. Programmatic text changes made while displaying history entries are excluded, preventing ordinary history navigation from overwriting the draft. Consequently, edits made to a recalled command are preserved and restored when the user navigates past the newest stored command.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to an AddressBookParser object, which in turn creates a parser that matches the command (e.g., DeleteCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., DeleteCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to delete a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

How the parsing works:

  • When called upon to parse a user command, the AddressBookParser class creates an XYZCommandParser (XYZ is a placeholder for the specific command name, e.g., AddCommandParser). The parser uses the other classes shown above to parse the user command and create an XYZCommand object (e.g., AddCommand). The AddressBookParser returns that object as a Command object.
  • All XYZCommandParser classes, such as AddCommandParser and DeleteCommandParser, implement the Parser interface so they can be treated similarly where appropriate, for example during testing.

Shared index and range parsing

Commands that operate on displayed persons can use IndexRangeParser to parse comma-separated indexes and inclusive index ranges.

For example, 1,3-5,7 represents displayed indexes 1, 3, 4, 5, and 7.

IndexRangeParser validates the expression, parses its indexes, sorts the result, and merges duplicate, overlapping, and adjacent ranges. It returns the canonical ranges in an immutable list. For example, 3-4,1,2-3,1,6,5 is canonicalized to 1-6.

The parser does not check whether the selected indexes exist in the currently displayed person list. That list depends on the current model state and active filter, so bounds validation is performed when the resulting command executes.

Command-specific parsers remain responsible for wrapping parsing failures in their own usage messages. This allows commands such as delete, edit, and future selection commands to share the same index-expression syntax while retaining command-specific feedback.

AddCommandParser treats h/TELEGRAM_HANDLE as optional, while EditCommandParser distinguishes an omitted h/ (preserve the current value) from an empty h/ (clear it). Both parsers explicitly reject the legacy a/ prefix.

ParserUtil performs shared contact-field normalization before constructing the corresponding model value object. It trims names and collapses consecutive internal whitespace. Name permits alphanumeric words separated by single spaces, hyphens or apostrophes within words, initials or abbreviations of up to three letters ending in a period when followed by another word, and one uppercase D/O or S/O between name parts. Because / normally ends a prefix, ArgumentTokenizer.containsUnknownPrefix treats an exact D/O or S/O token as name text only while n/ is the active prefix; elsewhere it is rejected as an unknown prefix. Lowercase s/o is not supported because s/ is the subject prefix. The model value objects enforce maximum lengths of 100 characters for names, subjects, and groups, 50 for tags, and 254 for email addresses, so command parsing and JSON reload apply the same constraints. A data file containing a longer value therefore fails to load, as described in the Storage component. Phone requires exactly eight digits, accepts single spaces or hyphens between digit groups, and stores numbers as xxxx xxxx. Country codes, +, and consecutive separators are rejected. TelegramHandle treats an empty value as absent; a non-empty value must begin with @, followed by 5 to 32 letters, digits, or underscores, with no leading underscore.

Model component

API : Model.java

The Model component,

  • stores the address book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • represents a person's Telegram contact using TelegramHandle; an empty value represents an omitted handle.
  • stores non-empty phone numbers as eight digits with a single space after the fourth digit (xxxx xxxx).
  • identifies people by name using Person.isSamePerson. Identity comparison ignores letter case, while the Name value object retains case-sensitive equality and preserves the spelling entered for storage and display. Therefore, distinct people with the same name cannot coexist (issue #97 remains unresolved).
  • stores tags in a LinkedHashSet, preserving entry order through parsing, editing, JSON storage, and display. Tag.equals and hashCode are case-insensitive; the first spelling supplied is retained when duplicates occur.
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in AddressBook, and each Person references tags from that list. This lets AddressBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both address book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonAddressBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

FileUtil writes replacement content to a temporary file in the destination directory before moving it over the destination. It uses an atomic replacement when supported by the file system and otherwise falls back to a regular replacement. If writing or moving fails, it attempts to remove the temporary file.

MainApp stores student data in data/tutortrack.json. If that file does not exist but a data file from an earlier version does (data/addressbook.json or addressbook.json), MainApp#migrateLegacyDataFileIfNeeded copies it to data/tutortrack.json and keeps the original as a backup. If the copy fails, TutorTrack continues to use the legacy file.

JsonAdaptedPerson deliberately reads and writes a person's TelegramHandle using the existing JSON "address" property; it does not introduce a "telegramHandle" property. When loading an older record, it replaces a non-empty physical address that does not begin with @ with an empty TelegramHandle in memory, while preserving the person. Values beginning with @ must also satisfy the current Telegram-handle format; otherwise, they are cleared. This is not a migration and no backup is created. The original JSON remains unchanged until the next successfully executed command causes LogicManager to save the in-memory data, at which point the old physical address is overwritten with an empty "address" value.

JSON files that already contain names differing only by capitalization, such as John Tan and john tan, now fail validation as duplicate data. Loading is all-or-nothing. If an existing data file cannot be loaded, for example because of such duplicates, a value longer than its maximum length, or malformed JSON, MainApp does not create Logic or the main window. Instead, it shows an error dialog naming the file and exits, so no command can save over the original file. An automatic migration would risk merging distinct students, so recovery is manual: back up and correct the file, or move it away to start again with sample data.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Delete command

DeleteCommandParser delegates its index-expression parsing to the shared IndexRangeParser, then constructs an IndexPersonTarget from the canonical ranges.

Each parsed component is represented by an IndexRange. An individual index is represented as a range whose start and end are equal.

IndexPersonTarget sorts and merges duplicate, adjacent, or overlapping ranges. For example, 1-3,2-4,4 is normalized to 1-4. This ensures that each contact is deleted at most once.

Before deleting any contacts, IndexPersonTarget resolves and validates every index against a snapshot of the currently displayed person list. Consequently, a command such as delete 1,999 fails without deleting contact 1 (suppose that contact index 999 does not exist).

DeleteCommand depends on the shared PersonTarget interface rather than directly on an index. This allows future implementations such as GroupDeleteTarget, SubjectDeleteTarget, and TagDeleteTarget to reuse the deletion workflow.

delete can also clear optional fields. When p/, h/, or t/ is present, DeleteCommandParser creates a DeleteCommand.FieldsToDelete record instead of deleting people. p/ and h/ must be empty and may each appear once. An empty t/ clears all tags, while named tags are parsed into a set, so a repeated name counts once. DeleteCommand#deleteFields builds every replacement Person before changing the model. If a named tag is missing from any selected person, it throws a CommandException and nobody is changed. Unlike deleting people, clearing fields keeps the current filter.

Edit command

EditCommandParser delegates parsing of the index expression to IndexRangeParser. This gives edit the same comma-separated index and inclusive-range syntax as other commands that operate on displayed persons.

The following diagram shows parsing, validation, tag edits, and constructor selection:

The parser rejects unknown parameter-like tokens such as x/typo, the legacy a/ prefix, and repeated non-tag prefixes. Shared value objects validate supplied fields: Phone requires eight digits and stores xxxx xxxx, while Email accepts hyphens inside domain labels, including the final label, which must be at least two characters long. Name accepts periods only after one-to-three-letter initials or abbreviations that precede another name word.

For backward compatibility, an index expression that selects exactly one index produces an EditCommand using the existing index-based constructor. This preserves the original single-person edit workflow and allows name, phone, email, Telegram handle, subject, group, and tags to be edited.

Single-person duplicate validation uses Person.isSamePerson, as does UniquePersonList.contains and UniquePersonList.setPerson. Names are compared without regard to letter case. Because setPerson first checks whether the target and edited person have the same identity, capitalization-only edits are allowed; the edited Person still contains the newly supplied Name, preserving its capitalization.

When multiple indexes are selected, EditCommandParser constructs an IndexPersonTarget. IndexPersonTarget implements the PersonTarget interface and resolves its ranges against the currently displayed person list when the command is executed.

IndexPersonTarget normalizes duplicate, overlapping, and adjacent ranges. It validates all selected indexes against a snapshot of the displayed list before returning any persons. Consequently, an invalid command such as edit 1,999 t/student fails without editing person 1.

Bulk edits are restricted to subject, group, and tags. Name, phone, email, and Telegram handle remain available only when exactly one person is selected. This policy is checked by both EditCommandParser and EditCommand. The parser provides early feedback for user input, while the command protects callers that construct commands directly.

The edit descriptor represents fields that were not supplied using null. A supplied subject or group replaces the corresponding value for every selected person. Tags are not replaced as a set. Instead, EditCommandParser turns each t/ value into a TagEdit: t/TAG becomes an addition and t/OLD_TAG,NEW_TAG becomes a rename. createEditedPerson applies these operations from left to right to a copy of each person's LinkedHashSet of tags, so unrelated tags and their order are preserved. A rename keeps the position of the source tag and removes any existing tag equal to the replacement, so the replacement's spelling is kept. Because Tag equality ignores case, matching ignores case too. If a rename source is missing, TagEdit#applyTo throws a CommandException. Empty p/, h/, and t/ values are rejected; optional fields are cleared using delete instead. Both command constructors copy the descriptor defensively, including the ordered tag edits.

For a bulk edit, all edited Person objects and the success result are prepared before the model is updated. The command then replaces each selected person using the resolved selection, so changes to the filtered list cannot cause later selected people to be skipped.

Both single and bulk edits leave the current filter active. The filtered list is reevaluated as people are replaced, so edited people that no longer match disappear from the view. In contrast, delete resolves indexes against the currently displayed list and resets a successful deletion to show all remaining people. LogicManager saves the address book after successful execution.

Find command

FindCommandParser accepts the n/, h/, s/, g/, and t/ prefixes. It rejects input that has no criterion, a non-empty preamble, an unknown prefix, or a repeated prefix. Name input is split on commas. Each term is either an unquoted keyword or a quoted phrase, and a blank phrase such as " " is rejected. NameContainsSearchTermsPredicate matches a keyword against whole name components, which are separated by spaces, hyphens, or apostrophes. It matches a phrase as a substring of the name. Both comparisons ignore case.

FindPredicate combines the optional name predicate with the optional Telegram handle, subject, group, and tag criteria. A person must satisfy every criterion supplied. A tag expression separated by , uses TagMatchMode.ANY, and one separated by & uses TagMatchMode.ALL; mixing both separators is rejected. FindCommand passes the predicate to Model#updateFilteredPersonList, and the UI updates because it observes the filtered list.

Clear confirmation

AddressBookParser turns clear into ClearCommand(false) and clear confirm into ClearCommand(true); any other argument is rejected. LogicManager records whether a confirmation is pending. An unconfirmed ClearCommand only sets this flag and returns a prompt, so nothing is saved. clear confirm empties the student list only when the flag is set; otherwise, it reports that no confirmation is pending. Any other input, including input that fails to parse, resets the flag, so the confirmation must immediately follow clear.

Appendix: Requirements

Product scope

Target user profile:

  • is a teaching assistant or tutor managing many students
  • teaches one or more modules or tutorial groups
  • needs to retrieve and update student particulars quickly
  • prefers desktop applications
  • can type quickly
  • prefers typing to mouse interactions
  • is reasonably comfortable using CLI-style commands

Value proposition:

TutorTrack helps teaching assistants manage student information efficiently in one place, including contact details, modules, and tutorial groups, using fast keyboard-based commands.

Use cases

(For all use cases below, the System is the TutorTrack and the Actor is the user, unless specified otherwise)

Use case: Add a student

MSS

  1. TA requests to add a student with a name, email, subject, and group, plus any optional particulars.
  2. TutorTrack validates the supplied particulars.
  3. TutorTrack adds the student.
  4. TutorTrack confirms that the student was added.

Use case ends.

Extensions

  • 2a. The supplied name or particulars are invalid.

    • 2a1. TutorTrack shows the corresponding error message.
    • Use case ends.

  • 2b. A student with the same name, ignoring letter case, already exists.

    • 2b1. TutorTrack shows an error message.
    • Use case ends.

Use case: Edit a single student's particulars

MSS

  1. TA requests to edit one student, identified by their index in the displayed list.
  2. TutorTrack finds the student at that index.
  3. TutorTrack validates the new particulars.
  4. TutorTrack updates the specified particulars.
  5. TutorTrack confirms that the student record was updated.

Use case ends.

Extensions

  • 2a. The index is not in the displayed list.

    • 2a1. TutorTrack shows an error message.
    • Use case ends.

  • 3a. One or more new particulars are invalid.

    • 3a1. TutorTrack shows the corresponding error message.
    • Use case ends.

  • 3b. The new name is already used by another student, ignoring letter case.

    • 3b1. TutorTrack shows an error message.
    • Use case ends.

Capitalization-only name edits refer to the same selected student and are accepted. The replacement Name is stored, so the newly entered capitalization appears in subsequent displays and saves.

Use case: Edit multiple students' common particulars

MSS

  1. TA requests to edit students identified by displayed indexes or index ranges.
  2. TutorTrack validates the index expression and supplied particulars.
  3. TutorTrack resolves the indexes against the currently displayed student list.
  4. TutorTrack updates the supplied subject, group, or tags for every selected student.
  5. TutorTrack confirms which student records were updated.

Use case ends.

Extensions

  • 2a. The index expression or a supplied particular is invalid.

    • 2a1. TutorTrack shows the corresponding error message.
    • Use case ends.

  • 2b. No field to edit is supplied.

    • 2b1. TutorTrack informs the TA that at least one field must be provided.
    • Use case ends.

  • 2c. A name, phone number, email address, or Telegram handle is supplied.

    • 2c1. TutorTrack informs the TA that only subject, group, and tags can be edited for multiple students.
    • Use case ends.

  • 3a. One or more indexes do not exist in the currently displayed list.

    • 3a1. TutorTrack shows an error message without editing any student.
    • Use case ends.

Use case: Delete students

MSS

  1. TA requests to list or find students.
  2. TutorTrack shows the matching students.
  3. TA requests to delete one or more students by their displayed indexes or index ranges.
  4. TutorTrack deletes the selected students and confirms which students were deleted.

Use case ends.

Extensions

  • 2a. The list is empty.

    • Use case ends.

  • 3a. The index expression is invalid, or an index is not in the displayed list.

    • 3a1. TutorTrack shows an error message without deleting any student.
    • Use case resumes at step 2.

Use case: List students from a tutorial group

MSS

  1. TA requests to list students from a specified tutorial group.
  2. TutorTrack validates the tutorial group.
  3. TutorTrack finds students belonging to that tutorial group.
  4. TutorTrack displays the matching students.

Use case ends.

Extensions

  • 2a. The supplied tutorial group is invalid.

    • 2a1. TutorTrack shows an error message.
    • Use case ends.

  • 3a. No students belong to the specified tutorial group.

    • 3a1. TutorTrack informs the TA that no students were found.
    • Use case ends.

Non-Functional Requirements

  1. Should work on any mainstream OS as long as it has Java 25 or above installed.
  2. Should be able to hold up to 1000 persons without noticeable sluggishness in performance for typical usage.
  3. A user with above average typing speed for regular English text (i.e. not code, not system admin commands) should be able to accomplish most of the tasks faster using commands than using the mouse.
  4. Normal operations should complete within 1 second for 200 records.
  5. Should save data locally in a human-editable text file.
  6. Should preserve data after being closed and reopened.
  7. Should prevent partially written files during saving.
  8. Should provide clear confirmation for destructive operations.
  9. Should validate all user-entered and imported data.
  10. Should not transmit student data to external services.
  11. Should provide clear error messages and usage instructions.
  12. Should support keyboard or command-based interaction for core tasks.
  13. Should work on Windows, Linux, and macOS using Java 25.
  14. Should work without an installer.
  15. Should not require a remote server.
  16. Should not exceed 100 MB.
  17. Should remain usable at the required screen resolutions and display scales.
  18. Should not require an internet connection for core functionality.

Glossary

  • TA: Teaching Assistant.
  • Tutorial Group: A tutorial class or group that a student belongs to.
  • Module/Subject: An academic course associated with a student, e.g. CS1231S.
  • Student particulars: Information stored about a student, such as name, phone number, email, module/subject, and tutorial group.
  • CLI-style command: A text command entered by the user to perform an action in TutorTrack.
  • Mainstream OS: Windows, Linux, and macOS.
  • Displayed list: The list of students currently shown, which may be filtered by find. Command indexes refer to this list.
  • Index range: An inclusive range of displayed indexes written as START_INDEX-END_INDEX, for example 3-5.

Appendix: Instructions for manual testing

Given below are instructions to test the app manually.

Note: These instructions only provide a starting point for testers to work on; testers are expected to do more exploratory testing.

Launch and shutdown

  1. Initial launch

    1. Download the JAR file and copy it into an empty folder.

    2. Double-click the JAR file, or open a terminal in that folder and run java -jar tutortrack.jar.
      Expected: The GUI opens with a set of sample students. The window size may not be optimal.

  2. Saving window preferences

    1. Resize the window to an optimal size. Move the window to a different location. Close the window.

    2. Relaunch the app by double-clicking the JAR file.
      Expected: The most recent window size and location are retained.

Deleting students

  1. Deleting contacts while all persons are being shown

    1. Prerequisites: List all persons using the list command, with at least 6 persons in the list, as in the sample data.

    2. Test case: delete 1
      Expected: The first contact is deleted from the list. The status message shows the deleted contact's details.

    3. Test case: delete 1,3,5-6
      Expected: The 1st, 3rd, 5th and 6th contacts are deleted from the list. The status message shows the deleted contacts' details.

    4. Test case: delete 0
      Expected: No person is deleted. The status message shows error details.

    5. Other incorrect delete commands to try: delete, delete x, ... (where x is larger than the list size)
      Expected: Similar to previous.

  2. Deleting a contact from a filtered list

    1. Prerequisites: Filter the displayed person list using find n/Alex.

    2. Test case: delete 1
      Expected: The first contact in the displayed list is deleted. The list then shows all remaining contacts.

  3. Clearing optional fields

    1. Prerequisites: Launch the application with the sample data and run list.

    2. Test case: delete 1 p/ h/
      Expected: The first student's phone number and Telegram handle are removed. The student is not deleted.

    3. Test case: delete 1 t/Missing
      Expected: No student is changed. The status message states that the tag does not exist.

Adding students

  1. Adding a student with all fields

    1. Test case: add n/Alice Tan p/91234567 e/alice@example.com h/@alice_tan s/Mathematics g/Sec 3A t/Student
      Expected: Alice is added. The phone is displayed as 9123 4567, and all supplied fields are shown.

  2. Adding a student without optional fields

    1. Test case: add n/Bob Lee e/bob@example.com s/Physics g/J1A
      Expected: Bob is added without a phone number, Telegram handle, or tags; no empty contact labels are shown.

  3. Adding a student whose name contains initials or a short abbreviation

    1. Test case: add n/Aisyah Bte. Ahmad e/aisyah@example.com s/Mathematics g/T11
      Expected: Aisyah is added with the name stored as Aisyah Bte. Ahmad.

    2. Test case: Replace the name above with John..Tan, .John, or John..
      Expected: No student is added. The status message shows the name constraints.

  4. Adding a student whose name contains D/O or S/O

    1. Test case: add n/Ravi S/O Kumar e/ravi@example.com s/CS2103T g/T11
      Expected: Ravi is added with the name Ravi S/O Kumar and the subject CS2103T.

    2. Test case: add n/Ravi Kumar e/ravi2@example.com s/CS2103T g/T11 S/O
      Expected: No student is added. The status message shows the add command usage because S/O is not part of the name.

  5. Rejecting values longer than their maximum length

    1. Test case: add n/Dan Ong e/dan@example.com s/CS2103T g/T11 t/ followed by 51 letters, for example aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa.
      Expected: No student is added. The status message states that tags can have at most 50 characters.

  6. Rejecting malformed input without changing data

    1. Test case: add n/Charlie Lim e/charlie@example.com s/Mathematics g/T11 x/typo
      Expected: No student is added. The status message shows the add command usage because x/ is unknown.

    2. Test case: Repeat either successful command above with the same name but different contact details.
      Expected: No second student is added. The status message reports that the student already exists.

Editing students

  1. Editing one student

    1. Prerequisites: Launch the application with the sample data and run list.

    2. Test case: edit 2 n/Betsy Crower t/friends,Graduate
      Expected: The 2nd student is renamed to Betsy Crower, and the tag friends is renamed to Graduate. Other tags are unchanged.

    3. Test case: edit 1 t/Missing,Graduate
      Expected: No student is changed. The status message states that the tag does not exist.

    4. Test case: edit 1 p/
      Expected: No student is changed. The status message states that edit values cannot be empty.

  2. Editing several students

    1. Test case: edit 1-3 g/T11 t/Online
      Expected: The first three students are moved to group T11 and gain the tag Online.

    2. Test case: edit 1-2 p/91234567
      Expected: No student is changed. The status message states that only subject, group, and tags can be edited for multiple students.

Finding students

  1. Finding contacts with keywords and phrases

    1. Prerequisites: Launch the application with the sample contacts.

    2. Test case: find n/"Alex Yeoh",Li
      Expected: Alex Yeoh and David Li are displayed because each matches at least one search term.

    3. Test case: find n/"Alex Yeoh","David Li"
      Expected: Alex Yeoh and David Li are displayed.

    4. Incorrect command: find n/Alex,"Yeoh
      Expected: The displayed list remains unchanged. The status message shows the find command usage.

    5. Incorrect command: find n/" "
      Expected: The displayed list remains unchanged. The status message shows the find command usage.

Clearing all students

  1. Clearing with confirmation

    1. Test case: clear
      Expected: No student is deleted. The status message asks you to enter clear confirm.
